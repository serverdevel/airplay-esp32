# Вклад

<a id="requirements"></a>
## Требования

ESP-IDF **v5.5.5 или новее**. Sendspin, который по умолчанию встроен практически в каждое изображение,
нужен обратный вызов WebSocket после рукопожатия, который появился в версии 5.5.5; на более старой версии 5.5.x
выпустите сборку с `CONFIG_SENDSPIN_ENABLE=n`. PlatformIO получает соответствующий набор инструментов от
платформа pioarduino закреплена в `platformio.ini`, поэтому ручная установка ESP-IDF не требуется.
для этого маршрута. Клонировать с подмодулями:

```bash
git clone --recursive https://github.com/rbouteiller/airplay-esp32
```

<a id="formatting"></a>
## Форматирование

Файлы C и заголовки отформатированы с помощью `clang-format` 22.1.4 в стиле LLVM: отступ в 2 пробела,
Ограничение в 80 столбцов. См. `.clang-format`.

```bash
python3 -m pip install --user -r requirements-dev.txt
scripts/format.sh           # format everything
scripts/format.sh --check   # check without modifying
```

<a id="linting"></a>
## Линтинг

`clang-tidy` работает с проверками на наличие ошибок, производительностью, переносимостью и читабельностью.
настроен в `.clang-tidy`. Ему нужен `build/compile_commands.json`, поэтому сначала соберите один раз.

```bash
scripts/lint.sh         # check
scripts/lint.sh --fix   # attempt auto-fixes
```

<a id="pre-commit-hook"></a>
## Хук pre-commit

Перехватчик автоматически форматирует промежуточные файлы C и H и запускает clang-tidy. Включите его один раз для каждого клона:

```bash
git config core.hooksPath .githooks
```

<a id="branches"></a>
## Ветки

**Открывайте запросы на извлечение для `staging`, а не `main`.**

`staging` — ветка интеграции. Каждое нажатие на него перестраивает матрицу прошивки и
заменяет предварительную версию `beta`, поэтому все, что там объединено, немедленно становится доступным.
устанавливается из [установщика браузера](getting-started/flashing.md#beta-builds) и может
быть опробован на реальном оборудовании, прежде чем он дойдет до тех, кто запускает выпуск.

`main` содержит стабильные выпуски. Это то, с чего публикуется сайт документации и
чему служат кнопки установки релиза, и он двигается только тогда, когда `staging` себя зарекомендовал
и версия помечена.

`version.txt` на `staging` должен опережать последнюю версию, иначе бета-задание завершится неудачей, поэтому
ударьте его, как только выйдет релиз.

!!! warning "Перебазировать перед слиянием"

    Запрос на извлечение проверяется по `staging` **так, как это было во время проверки**. Если
    тем временем сливается еще один PR, при слиянии зеленая галочка может стать красной — две ветки
    которые затрагивают разные файлы, сливаются без конфликтов, но все равно могут нарушить сборку
    вместе, именно так уже однажды переполнился раздел SPIFFS.
    Включите *Требовать актуальность ветвей перед слиянием* на `staging` или выполните перебазирование
    и дождитесь нового запуска, прежде чем объединять что-либо нетривиальное.

<a id="ci"></a>
## CI

При каждом запросе на получение `main` или `staging` и при каждом запросе на `main`:

| Работа | Что он делает |
| --- | --- |
| `format-check` | `clang-format` пробный прогон всех файлов C/H, за исключением `components/u8g2` |
| `lint-check` | `clang-tidy` против результатов сборки |
| `output-backends` | Создает выходные серверные части S/PDIF и USB, чтобы каждый серверный компонент продолжал связываться |
| `build` | Строит целевую матрицу |

Запрос на извлечение, который затрагивает только Markdown, пропускает задания прошивки, поэтому опечатка в документации не возникает.
стоимость сборки набора инструментов ESP-IDF.

Целевой список находится в `.github/workflows/targets.json`. Запрос на включение создает только
записи с пометкой `"core": true` — достаточно, чтобы охватить поддержку каждого чипа и каждой платы.
каталог — в то время как нажатие на `main` и `staging` собирает их все. Матрица
не дает быстрого сбоя, и бета-задание публикует все, что удалось, поэтому одна плата не может
компиляция не запрещает сборку любой другой платы.

Добавление цели означает запись в `targets.json` **и** соответствие
Манифест `docs/firmware/<name>.json`, `parts[0].path` которого
`airplay2-receiver-<name>.bin`. Рабочий процесс документации автоматически удаляет манифест, двоичный файл которого
отсутствует в выпуске, поэтому добавленная здесь цель отображается только в установщике браузера
как только релиз действительно его содержит.

Пометка `vMAJOR.MINOR.PATCH` запускает выпуск, который проверяет тег на соответствие
`version.txt` и публикует объединенные двоичные файлы прошивки.

<a id="testing"></a>
## Тестирование

Фреймворка модульного тестирования не существует — это встроенная прошивка, а тестирование означает перепрошивку.
настоящее оборудование. При отправке изменения укажите, какую плату и среду сборки вы тестировали.
дальше.

<a id="editing-these-docs"></a>
## Редактирование этих документов

Сайт создан с помощью [Zensical](https://zensical.org/) из Markdown в `docs/`. Каждый
страница имеет ссылку редактирования в правом верхнем углу, которая приведет вас прямо на GitHub.
редактор, поэтому небольшие исправления вообще не требуют локальной настройки.

Чтобы просмотреть локально:

```bash
python3 -m pip install -r docs/requirements.txt
zensical serve
```

Затем откройте <http://127.0.0.1:8000>.

Конфигурация находится в `mkdocs.yml`. Zensical изначально читает этот формат — это
преемник Material for MkDocs, созданный той же командой, поэтому файл не изменился по сравнению с
Настройка материала и обратное переключение — это всего лишь изменение зависимости.

Сборка выполняется в **строгом режиме**, поэтому неработающая внутренняя ссылка приводит к сбою CI, а не к доставке.
мертвая ссылка. Добавление страницы означает добавление ее в раздел `nav` `mkdocs.yml`.

Документы и код намеренно хранятся в одном репозитории: запрос на включение, изменяющий GPIO.
default или опция Kconfig должна обновить соответствующую страницу в том же файле diff.
